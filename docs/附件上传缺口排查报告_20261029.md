## 三、缺失清单（按优先级）

### 🔴 P1 — 业务上必须留存凭证/证据，缺失会导致流程断链

#### 1. 客户客诉（`/customer_complaint/`，模型 `CustomerComplaint`）
- **应有附件**：客诉现象照片、不良品照片、物流/签收单据、工程报告附件、8D 报告、赔偿协议、客户回复邮件截图。
- **现状**：模型无任何文件字段；表单 `CustomerComplaintForm` 无 `enctype`；列表/详情（`_customer_complaint_detail_modal.html`）无附件区；闭环表单 `CustomerComplaintClosureForm` 也无法带附件。
- **风险**：客诉处理强依赖证据留存，目前仅能靠文字描述，出事无法回溯；且模型已有 `engineering_report`、`closure_note` 等文本字段，缺文件是明显断档。
- **建议**：**多附件 + 阶段化**（受理证据 / 处理过程 / 闭环资料），复用 `ArchiveFile` 模式。

#### 2. 诉讼纠纷（`/complaint/`，模型 `Complaint`）
- **应有附件**：起诉状、证据清单及证据材料、庭审笔录、判决书、执行申请书/裁定。
- **现状**：模型无文件字段；`ComplaintForm` 无上传；`complaint_detail.html` 无附件区。
- **风险**：诉讼材料是最典型的「必须存档备查」内容，目前只能线下管理。
- **建议**：多附件，详情页分组展示（可参照样品阶段卡片）。

#### 3. 保险保单（`/insurance/`，模型 `Insurance`）
- **应有附件**：电子保单 PDF、批单、缴费凭证、理赔材料。
- **现状**：模型无文件字段；`InsuranceForm` 无上传；`insurance_detail.html` 无附件区。注意：证照（License）已有扫描件，**唯独保单本体没有**，形成「有证照扫描件、无保单」的倒挂。
- **风险**：出险理赔时找不到保单正本。
- **建议**：单文件 PDF（保单）+ 可选多附件（批单/凭证），与客户台账同款三重校验。

#### 4. 每日记录（`/daily_record/`，模型 `DailyRecord`）
- **应有附件**：工作成果截图、导出报表、现场照片（可选附件）。
- **现状**：模型无文件字段；表单/详情均无上传。
- **风险**：较低（文字为主），但周报/月报场景常需附成果文件。
- **建议**：P1 末位，轻量多附件即可；注意记录按 `user` 隔离，附件下载必须校验归属人。

## 五、两种落地方案对比

### 方案 A：通用附件模型（推荐）

新增一张通用附件表（如 `common.Attachment`，`GenericForeignKey` 或按模块 FK），配套一套上传/删除/预览视图和前端组件，11+ 个模块统一复用。

- **优点**：一次建设全部受益；校验/权限/留痕/文件清理逻辑只写一遍；后续新模块零成本接入；列表页「附件」列可做成统一模板片段。
- **缺点**：初次建设量稍大；GenericForeignKey 无法走数据库级联，需在信号或 service 层清理。
- **参照**：`ArchiveFile`（多附件 + 缩略图 + 逐个校验）与 `ProofAttachment`（阶段化 + 业务分组）两个现有实现已覆盖全部所需场景，取两者之长即可。

### 方案 B：逐模块加 FileField

与 `License.scan_file`、`CustomerLedger.attachment` 一致，哪个模块缺就在哪个模型加字段。

- **优点**：单模块改动小、直观，与台账模块现有代码风格一致。
- **缺点**：14 个模块就要写 14 套表单字段 + 校验 + 删除清理 + 模板；`validate_license_scan`、台账三重校验这类逻辑会反复复制粘贴，后续改规则要改多处。

### 工作量估算（方案 A，粗估）

| 事项 | 内容 |
|---|---|
| 通用附件模型 + 迁移 | 1 张表，字段：业务对象引用、文件、原始名、上传人、备注、排序 |
| 上传/删除/预览视图 + URL | 一套（含缩略图、鉴权、归属校验） |
| 统一校验 | 复用 `work_record/file_validation.py` + `samples/validators.py`，无需新写 |
| 前端组件 | 附件面板（列表 + 上传 + 删除）做成可 include 的模板片段 |
| 逐模块接入 | 每模块：表单/详情挂接 + 列表页附件列 + 留痕，约 0.5～1 人日/模块 |
| P1 四模块 | 约 3～4 人日；全部 14 项约 8～12 人日 |

## 六、可直接复用的现有基础设施

新增附件功能**不需要从零造轮子**，以下均已就绪：

1. **文件头/类型校验（全站唯一）**：`work_record/file_validation.py` — magic byte 表 + `magic_ok()` + `read_head()`，已统一过此前三处不一致的实现。
2. **统一上传校验器**：`samples/validators.py::validate_upload()` — 扩展名白名单 + 大小上限 + magic byte 双向校验，`AuditRecordForm` / `ProofAttachmentForm` 在用。
3. **分模块专用校验**：`archive/validators.py::validate_archive_file()`（档案附件）、`archive/forms.py::validate_license_scan()`（证照扫描件）。
4. **全局配置项**：`settings.PROOF_MAX_SIZE = 20MB`、`settings.PROOF_ALLOWED_EXT`（17 种扩展名白名单）。
5. **RBAC 权限**：`accounts/registry.py` 注册表 + `@perm_required("模块","动作")` 装饰器，附件上传/删除按模块权限走。
6. **操作留痕**：`archive` / `samples` 的 `_log()` 模式（上传附件、删除附件均写 `OperationLog`），照抄即可。
7. **前端模式**：`archive_detail.html` 的附件面板（缩略图 + 徽标 + 删除确认）、`customer_ledger_list.html` 的附件列 + 有/无筛选，均可作为模板片段抽取复用。
8. **删除时清理物理文件**：`records/views.py::_delete_ledger_attachment` 的 `after_delete` 钩子模式，避免删记录留孤儿文件。

## 七、建议实施顺序

1. **第一批（P1）**：客户客诉 → 诉讼纠纷 → 保险保单 → 每日记录。先立通用附件模型（方案 A），用客诉做首个接入样板（含阶段化分组）。
2. **第二批（P2）**：规章制度、核价比价、装修、客户信用评估、供应商档案、证照年审、知识文档。批量接入，每模块补列表页「附件」列。
3. **第三批（P3）**：评估试样/小批量记录是否已被样品证明材料覆盖后再决定；保险标的按需。
4. **收尾**：抽取统一附件面板模板片段；补充分级权限（上传/删除/下载分别授权）；补充测试（参照 `archive/tests.py`、`samples` 的校验测试）。
