## 一、背景

客户账期（`CustomerCredit`）、客户台账（`CustomerLedger`）、客户评审（`CustomerReview`）三个模块各自独立，客户信息重复录入，互相无关联。

现有数据：

| 项 | 数量 | 说明 |
|---|---|---|
| 客户账期单 | 70 张 | 去重 67 个客户，3 个客户各有 2 张（复审） |
| 客户台账 | 7 家 | 与账期单客户名零重合 |
| 客户评审单 | 2 张 | 模块刚上线 |

结论：台账不是全量客户主数据，不能作为客户名称唯一出处。同步来源只能是账期单自身，台账仅在同名时提供地址、账期参考。

## 二、现状走查（改造前）

客户：深圳市宏昌精密工业有限公司，代加工客户，业务员张伟，11-20 现场。

| # | 在哪里做 | 要手工录入什么 |
|---|---|---|
| 1 | 客户账期 → 新建 | 客户名称、业务员、客户类型、工作方式、现场日期 |
| 2 | 客户评审 → 新增现场审核表 | 客户名称再录一遍、类型再选一遍、审核地址手打、申请编号留空 |
| 3 | 在现场填审核表 | 7 项判定 |
| 4 | 客户评审 → 新增信用评价表 | 客户名称第三遍、12 项财务数据、23 项打分 |
| 5 | 回账期单填「结果」 | 同意账期 60 天、额度 150 万，再录一遍 |
| 6 | 事后追溯 | 翻两张表，靠日期猜对应关系 |

名称录 3 遍，业务员 2 遍，账期与评审之间无关联。

## 三、目标流程（改造后）

| # | 在哪里做 | 发生什么 |
|---|---|---|
| 1 | 客户账期 → 新建 | 客户名称框输入「宏昌」下拉出历史客户，选中后自动填客户细分、业务员（可改）；工作方式选现场审核；现场日期 11-20。保存后生成单号 `KQ-202611-018` |
| 2 | 账期详情 → 点「发起评审」 | 弹窗列出「客户现场审核表 + 客户信用评价表」，客户信息已填好、灰底只读，确认后一次生成两张单（表单编号 `CR-` 系列） |
| 3 | 在现场或回公司 | 两张单已在评审列表，打开填写，提交时服务端算分算等级 |
| 4 | 账期详情 → 自动出现「关联评审」 | 现场审核：符合 3 项、待整改 1 项；信用评价：78 分 B 级，建议额度 150 万，日期 11-21 |
| 5 | 账期单填「结果」 | 结果框旁灰色提示「建议：B 级 · 150 万」，结论由人填写 |

数据流单向：账期单 → 评审单 → 结论回读。无循环依赖。

## 四、已确认的四项决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 客户类型映射 | 账期单增加「客户细分」字段 `customer_segment`，档位经销商 / 终端客户 / 代加工客户（与评审单 `customer_type` 一致，直通取值）。账期原有 `customer_type` 两档（普通客户 / 代加工客户）不变，继续用于判断要不要去现场 |
| 2 | 结论回写 | 只读展示 + 建议值。系统不改账期单的「结果」字段 |
| 3 | 前期资料清单 | 两边都能编辑。落地方式：记录挂在账期单（单一数据源），评审单经关联反查同一批记录，两处只是编辑入口，天然一致 |
| 4 | 历史 70 张账期单 | 不回填、不跑脚本（`credit_no`、`customer_segment` 均留空）。「发起评审」按钮对所有账期单可用，详情页不加「未关联」标注 |

## 五、设计取舍

1. **存快照，不存引用。** 评审单生成时把客户名称、客户细分、业务员复制一份落库。账期单后续改名，已出具的评审单不变。审计依据是出具时点的数据。
2. **一单可挂多张。** 现场审核与信用评价是两次动作两张表；复审产生新一轮评审。`CustomerReview.source_credit`（`SET_NULL`）允许一张账期单对应多张评审单。
3. **结论只回读不自动写。** 「结果」是审批口径，写「同意 60 天」即对外承诺。系统给建议，人写结论；自动写入会让复审覆盖历史结论。
4. **不抽客户主表。** 台账 7 家、账期 67 家、零重合，抽主表需先清洗两套名单并改四个模块外键，收益不抵成本。待两边名册合流再评估。
5. **评审单是审计凭证，随账期单删除而独立存活。** `source_credit` 用 `SET_NULL`：账期单删除后评审单保留全部快照字段，仅失去反查入口。

## 六、字段映射与单号规则（发起评审时）

| 评审单字段 | 取值来源 | 规则 |
|---|---|---|
| 客户全称 | 账期单.customer_name | 复制，默认只读，需勾「手动修改」才能改 |
| 客户类型 | 账期单.customer_segment | 空（历史单未细分）时下拉停在空提示位，由填表人自选三档之一 |
| 表单日期 | 账期单.site_date，空则 proposal_date | 现场审核表取现场日期 |
| 审核地址 | 台账.address（按客户名精确匹配，有则带出） | 仅现场审核表，可改 |
| 陪同人员 | 账期单.salesperson | 可改 |
| 对应申请编号 | 账期单.credit_no | 自动写入，只读；历史单 `credit_no` 为空时留空，灰条以「账期 #id」标识来源 |
| 结算方式 | 台账.payment_terms（同名才有） | 可改 |
| 表单编号 | 自动生成 CR-YYYYMM-序号 | 保存时生成（当月最大序号 +1，按 `review_no` 前缀查询）；手工新增评审单仍可手填，非空不覆盖 |

单号规则（P1 新增）：

| 字段 | 模型 | 生成时机 | 规则 |
|---|---|---|---|
| credit_no | `CustomerCredit`（新增字段，null=True, blank=True） | `make_form_view` 的 `after_save` 钩子，`created=True` 时 | `KQ-YYYYMM-序号`，序号取当月已有最大值 +1；空串统一转 `None` 落库（照 `archive_no` 先例），为未来唯一约束留路 |
| review_no | `CustomerReview`（已有字段） | 发起评审生成的两张单保存时 | `CR-YYYYMM-序号` 同规则生成；手工新增仍可手填，非空不覆盖 |

## 七、界面改动

**A. 客户账期表单**

- 客户名称输入框加历史客户下拉（datalist，输入即提示，不强制选）
- 选中历史客户后自动填客户细分、业务员，可改
- 客户类型下方灰字提示：普通客户建议现场审核，代加工客户建议内部流程。仅提示，不改工作方式
- 适配 AJAX 弹窗双模式：整页表单与 `_form_modal.html` 弹窗两条渲染路径都要带历史客户数据

**B. 客户账期详情页**

- 顶部按钮区：返回列表 / 编辑记录 / **发起评审** / 删除记录（发起评审按钮用 `{% can "customer_review" "create" %}` 控制显示）
- 详情行新增：单号（`credit_no`，空显示「无」）、客户细分（空显示「未细分」）
- 「前期资料」清单块：6 项三态（未收集 / 已收集 / 不适用）+ 收集日期 + 附件 + 备注
- 「关联评审」表格块：类型 / 编号 / 日期 / 得分或结论 / 等级 / 额度建议 / 状态；空态显示「尚未发起评审」。仅进整页详情页，`_customer_credit_detail_modal.html` 弹窗保持精简不加

**C. 客户评审表单**

- 顶部只读灰条：由账期单 KQ-202611-018 发起（历史单无单号时显示「由账期单 #id 发起」），客户信息以账期单为准
- 客户全称、客户类型灰底只读，勾「手动修改」解锁
- 表单编号自动生成

**D. 客户评审详情页**

- 顶部灰条同 C；「前期资料」只读展示（入口 2）

## 八、实现细节约束（实施时遵守）

1. **服务端快照兜底。** 前端 disabled 字段不随 POST 提交：`review_add` 视图在 `source_credit` 存在时，对只读字段（customer_name / customer_type / apply_no）一律以账期单快照值强制覆盖，仅在 POST 带「手动修改」标记时放开 customer_name。不信任前端状态。
2. **datalist 数据注入。** `crud.make_form_view` 目前只向模板传 `{form, title}`，需扩展支持 `extra_context`（历史客户名册：名称 + 细分 + 业务员，一次 `values_list` 去重即可，67 家量级无需接口）；整页与 `_modal` 两条渲染路径同传。
3. **发起评审视图权限。** 挂在 `customer_credit` 详情页、创建 `customer_review` 记录：视图用 `@perm_required('customer_review', 'create')`，账期读权限不等于评审创建权。两张单一次事务生成，均写 `source_credit` 与快照，均走 `log_operation` 留痕。
4. **P3 穿行测试分支。** 穿行测试对象含供应商（`PAYEE_TYPES`），仅 `payee_type='客户'` 时才按客户名取最近一张有 `approved_terms_days` 的账期单作建议值；历史账期单无批准账期，查不到即回退现有手填行为，表单给灰字建议提示而非强改。
5. **导入匹配维持两级。** `_match_review` 保持「表单编号 →（客户全称 + 表单日期 + 类型）」不新增申请编号匹配；导入页说明不提申请编号。自动编号的单子导出再导入按 `review_no` 正确匹配自己。
6. **测试。** 项目已有 `tests_customer_review_io.py` 习惯：发起评审（含事务性、快照覆盖、权限拒绝）、单号生成（含空串转 None）、`SET_NULL` 删除语义需配套用例。
7. **P2 附件清理。** `CustomerCreditDoc.attachment` 删除时照 `CustomerLedger.attachment` 钩子清理物理文件；账期单删除时资料记录与文件级联清理。

## 十、风险与注意

| 风险 | 处置 |
|---|---|
| 历史账期单客户细分字段为空，生成评审单时客户类型缺值 | 下拉停在空提示位由填表人自选三档之一；账期表单保存新单时细分必填 |
| 同名不同司（深圳/中山同名简称） | 名称下拉只做提示不强制；台账地址仅在名称精确相等时带出 |
| 评审结论与账期「结果」不一致 | 详情页并列展示，不做一致性强校验；账期编辑时给出对比提示 |
| 附件重复上传（账期与评审各传一份营业执照） | 前期资料附件挂在账期单，评审侧只读引用，不重复存 |
| 前端绕过只读改客户名 | 服务端强制快照覆盖（见实现细节约束 1） |
| 删除账期单导致评审单悬空 | `SET_NULL` + 快照自足，评审单完整保留（见设计取舍 5） |
| 单号并发撞号 | 内网低频，应用层取当月最大 +1 即可；`credit_no` 空值存 NULL 为后续唯一约束留路 |
